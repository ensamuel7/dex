DexLang

A statically-typed language that compiles to C. Fast builds, native binaries, built-in HTTP/WebSocket servers, JSON serialization, database access, and concurrency.

Getting Started

Installation

One-line install (macOS / Linux):

curl -fsSL https://raw.githubusercontent.com/ensamuel7/dex/main/install.sh | sh

This downloads the latest prebuilt binary for your platform and installs it to /usr/local/bin.

Prerequisites

You need a C compiler since dex compiles to C:

  • macOS: xcode-select --install
  • Ubuntu/Debian: sudo apt install gcc
  • Fedora: sudo dnf install gcc

Windows

On Windows, dex runs under WSL2, the Linux environment built into Windows 10 and 11. The compiler and the programs it builds are Linux binaries there, so everything on this site works as written. In PowerShell, as administrator:

wsl --install

Restart when it asks, open Ubuntu from the Start menu, and install a C compiler and dex inside it:

sudo apt update && sudo apt install -y gcc curl
curl -fsSL https://raw.githubusercontent.com/ensamuel7/dex/main/install.sh | sh
  • Keep projects in the Linux file system, under ~, not under /mnt/c. Building reads and writes many files, and crossing into the Windows drive is several times slower.
  • Edit in VS Code with Microsoft's WSL extension: run code . in a project folder inside Ubuntu, then install the Dex extension when VS Code offers to install it in WSL. It then uses the dex inside Linux.
  • Servers are reachable from Windows. A program listening on port 8080 in WSL answers at http://localhost:8080 in a Windows browser.
  • Docker Desktop works too: the Docker image below runs the same way from PowerShell.

From source

If you have Go (1.25+) installed:

go install github.com/ensamuel7/dex@latest

Or build manually:

go build -o dex && sudo mv dex /usr/local/bin/

Your first program

Create hello.dx:

import "fmt"

fn main(): void {
    fmt.println("Hello, World!")
}

Build & Run

dex build hello.dx    # produces ./hello binary
dex run hello.dx      # build + run, cleans up after

After building, the binary is a standalone native executable that can be called directly:

dex build hello.dx
./hello               # run the compiled binary directly

Docker

The image ensamuel7/dexlang has dex and everything it compiles with: gcc, git, and the headers for SQLite, PostgreSQL, OpenSSL, libcurl and hiredis. You need nothing else installed, which makes it a good fit for CI, or for trying the language without installing it.

docker pull ensamuel7/dexlang:latest

The entrypoint is dex and the working directory is /workspace, so mount your project there and pass a command:

docker run --rm -v "$(pwd):/workspace" ensamuel7/dexlang run hello.dx
docker run --rm -v "$(pwd):/workspace" ensamuel7/dexlang test
docker run --rm -v "$(pwd):/workspace" ensamuel7/dexlang build hello.dx

# a server needs its port published
docker run --rm -p 8080:8080 -v "$(pwd):/workspace" ensamuel7/dexlang run server.dx

build writes a Linux binary to build/, so it runs in a container or on a Linux server, not on a Mac or Windows host. On a Linux host, add --user "$(id -u):$(id -g)" so build/ belongs to you rather than to root.

To ship a program in its own image, build in the dex image and copy only the binary into a small one:

FROM ensamuel7/dexlang:latest AS build
WORKDIR /src
COPY . .
RUN dex build main.dx

FROM debian:trixie-slim
RUN apt-get update && apt-get install -y --no-install-recommends \
        libsqlite3-0 libpq5 libssl3t64 libcurl4t64 \
    && rm -rf /var/lib/apt/lists/*
COPY --from=build /src/build/main /usr/local/bin/app
EXPOSE 8080
CMD ["app"]

A project with a dex.mod needs its libraries fetched first: add RUN dex mod download before the build. Without a dex.mod that command fails, so leave it out.

The runtime image must be the same Debian release the dex image is built on (13, "trixie"), because the binary links against that release's libraries.

The binary links only the libraries for the modules it imports. A program using nothing beyond fmt needs libc alone, so the apt-get line can go. To see exactly what one needs: docker run --rm -v "$(pwd):/workspace" --entrypoint ldd ensamuel7/dexlang build/main.

latest follows each release. For a build that must not change under you, pin a version instead: the image tags are listed on Docker Hub, and every release is on the Versions page.

Variables

Variables are declared with let. You can provide an explicit type annotation or omit it and let the compiler infer the type automatically.

// Explicit type annotation
let x: int = 42
let name: string = "hello"
let flag: bool = true
let nums: int[] = [1, 2, 3]

Type Inference

DexLang supports type inference — when the type can be determined from the right-hand side of an assignment, the type annotation is optional. The compiler will infer the correct type at compile time.

let y = 100        // inferred as int
let pi = 3.14      // inferred as double
let msg = "world"  // inferred as string
let ok = true      // inferred as bool
let ch = 'A'       // inferred as char

A whole-number literal is always inferred as int. For a long, write the type: let big: long = 1000000.

Inference also works with expressions, function returns, and struct constructors:

let sum = 10 + 20       // inferred as int
let half = 10.0 / 3.0   // inferred as double
let nums = [1, 2, 3]    // inferred as int[]
let words = ["a", "b"]  // inferred as string[]

Multi-Declaration

Multiple variables of the same type can be declared on one line.

let x, y, z: int = 0
let a, b: string?  // both default to null
const width, height: int = 100

Multi-declaration requires an explicit type annotation.

Redeclaration

A name can be declared once per scope. A second let of the same name in the same block, or of a parameter's name in a function body, is a compile error; assign to the existing variable instead. A nested block may declare the name again, hiding the outer one until the block ends.

let n: int = 1
let n: int = 2      // error: 'n' is already declared in this scope
n = 2               // fine
if (n > 0) {
    let n: int = 3  // fine: a new scope
}

Assignment

A variable must be declared with let before it can be assigned.

x = 20
name = "DexLang"

Compound Assignment & Increment

These operators work on numeric variables (int, long, double).

x += 5  // equivalent to x = x + 5
x -= 2  // equivalent to x = x - 2
x++     // equivalent to x = x + 1
x--     // equivalent to x = x - 1

Built-in Functions

assert(condition: bool) — if the condition is false, prints a failure message to stderr and exits with code 1. Used for testing. The message carries the file, the line and the condition as it was written, because a test file is a main() full of asserts and "assert failed" on its own meant bisecting by hand to find which one:

FAIL: examples/generics_test.dx:84: assert(identity(42) == 42)
assert(1 + 1 == 2)
assert(x > 0)

Testing

Test files use the *_test.dx naming convention. Use assert() to validate behavior. Run with dex test (discovers all *_test.dx files) or dex test myfile_test.dx.

// math_test.dx
fn main(): void {
    assert(1 + 1 == 2)
    assert(10 % 3 == 1)
}

Functions & Control Flow

Functions

Functions are declared with fn or function. Both are equivalent:

fn add(a: int, b: int): int {
    return a + b
}

function main(): void {
    fmt.println("hello")
}

Default Parameters & Named Arguments

A parameter can declare a default with = value, and a call may leave it out. An argument can name the parameter it is for, in any order, so a call reads as what it passes:

fn page(from: string, to: string, limit: int = 25, offset: int = 0): Row[] { ... }

page(start, end)
page(from: start, to: end, limit: 10, offset: 0)
page(start, end, offset: 50)
sessionStore.list(db, filter, limit: 10, offset: 0)

page(start, end) takes both defaults, and page(start, end, offset: 50) keeps the default limit. Positional arguments come first; named ones fill the rest and anything unfilled takes its default. An unknown name, a duplicate, or a missing required parameter is a compile error. Named arguments work on any function or method declared in Dex, including one in an imported module; a stdlib function, an external C function, a constructor or a function value has no parameter names, so naming an argument there is an error rather than being silently ignored.

Control Flow

if / else

else if chains are supported. The condition must be bool and enclosed in parentheses.

if (x > 0) {
    fmt.println(x)
} else {
    fmt.println(0)
}

while

Loop while a condition is true:

let i: int = 0
while (i < 10) {
    fmt.println(i)
    i = i + 1
}

for

C-style for loop with init, condition, and post statements. The post statement supports ++, --, +=, -=, or =.

for (let i: int = 0; i < 10; i++) {
  fmt.println(i)
}

// Type inference works in the init statement
for (let i = 0; i < 100; i += 2) {
  // iterate by 2
}

foreach

Iterate over array elements. The iterable must be an array type. The index variable (if used) is always int. The value variable takes the element type of the array.

let nums: int[] = [10, 20, 30]

// Value only
foreach (nums as n) {
    fmt.println(n)
}

// Index and value
foreach (nums as i, n) {
    fmt.println(i)  // 0, 1, 2
    fmt.println(n)  // 10, 20, 30
}

break and continue

Exit a loop early with break, or skip to the next iteration with continue. Both work inside while, for, and foreach loops. Using them outside a loop is a compile error.

while (true) {
    if (done) {
        break
    }
}

for (let i = 0; i < 10; i++) {
    if (i % 2 == 0) {
        continue
    }

    fmt.println(i)  // prints odd numbers only
}

switch

Multi-way branching on a value. Supports int, string, char, long, double, and bool tag types. Multiple values per case are separated by commas. There is no fallthrough — only the matched case executes.

switch (action) {
    case "start": {
        fmt.println("starting")
    }
    case "stop", "pause": {
        fmt.println("not running")
    }
    default: {
        fmt.println("unknown")
    }
}

// Integer switch
switch (code) {
    case 200: {
        fmt.println("OK")
    }
    case 404: {
        fmt.println("Not Found")
    }
    default: {
        fmt.println("Other")
    }
}

Optional Types

Append ? to any type to make it optional. Optional types can hold either a value of the inner type or null.

let x: int? = 5        // has a value
let y: int? = null     // no value
let z: int?            // defaults to null
let s: string? = null  // optional string

Null Checks & Type Narrowing

Use == null or != null to check if an optional has a value. Inside an if block guarded by a null check, the variable is automatically narrowed to the inner (non-optional) type.

let x: int? = 5
if (x != null) {
    // x is narrowed to int here
    let y: int = x + 1
}

Functions with Optional Types

Functions can accept and return optional types:

fn findUser(id: int): string? {
    if (id == 1) {
        return "Alice"
    }

    return null
}

fn greet(name: string?): void {
    if (name != null) {
        fmt.println(name)
    }
}

Constants

Declare immutable variables with const. Constants cannot be reassigned, incremented, decremented, or modified with compound assignment after initialization. const supports the same syntax as let — both explicit type annotations and type inference work.

const pi = 3.14
const max_size: int = 100
const name: string = "DexLang"

Immutability

Attempting to modify a const variable is a compile error:

const x = 42
x = 10  // ERROR: cannot reassign const variable 'x'
x++     // ERROR: cannot modify const variable 'x'
x += 5  // ERROR: cannot modify const variable 'x'

Arrays

Array Basics

Arrays are declared with a typed bracket syntax. Elements are accessed and assigned by index, and built-in methods handle common operations:

let nums: int[] = [10, 20, 30]
let first: int = nums[0]      // indexing
nums[1] = 25                  // index assignment
nums.push(40)                 // append
let length: int = nums.len()  // length

Slicing

Use arr[start:end] to create a new array from a sub-range. Start is inclusive, end is exclusive. Either bound can be omitted:

let nums: int[] = [10, 20, 30, 40, 50]
let mid: int[] = nums[1:4]  // [20, 30, 40]
let head: int[] = nums[:3]  // [10, 20, 30]
let tail: int[] = nums[3:]  // [40, 50]

The result is always a new array. Start and end are clamped to valid bounds. Slicing works on all array types (int[], string[], bool[], struct arrays, etc.).

StringBuilder

StringBuilder is a built-in type for efficiently building strings via a growable buffer. It avoids the O(n²) cost of repeated string concatenation in loops. No import is needed.

Creating a StringBuilder

let sb = StringBuilder()
sb.append("hello ")
sb.append(42)
let result: string = sb.toString() // "hello 42"

The primary use case is building strings in loops without O(n²) overhead:

    sb.append(str.fromInt(i))
    sb.append(",")

Enums

Enums define named sets of integer constants. Variants are assigned sequential integer values starting at 0.

Enum Definition

enum Color {
    Red
    Green
    Blue
}

Enum Usage

let c: Color = Color.Red

Maps

Maps are hash tables with typed keys and values. They are heap-allocated with reference counting.

Supported Types

Creating Maps

let m: map[string, int] = {}

let scores: map[string, int] = {}

// Write
scores.set("alice", 100)
scores.set("bob", 7)

let a: int = scores.get("alice")       // 100

String Methods

String Interpolation

A ${...} inside a string literal substitutes the value of the expression inside it:

let n = 7
let name = "dex"
let s = "n=${n} name=${name} sum=${n + 1}"  // "n=7 name=dex sum=8"
fmt.println("inline ${n}")
  • Any expression goes inside, not only a name — ${n + 1}, ${arr[0]}, ${describe(n)}. A call inside an interpolation runs exactly once.
  • Every primitive converts without a cast: int, long, double, bool, char and string. A double renders the way %g does, so 1.5 is "1.5".
  • Any other type goes through the same conversion as string uses, so a struct renders as Point{x: 1, y: 2}.
  • The parts are appended to a StringBuilder and built once, so a literal with several interpolations costs one allocation for the result rather than one per concatenation.

Interpolation is a string literal feature — a tag is raw and does not interpolate.

String variables have built-in methods for common text operations. No import is needed.

Structs

Struct Declaration

Structs define composite types with named, typed fields:

struct Point {
    x: int
    y: int
}

struct User {
    name: string
    age: int
    active: bool
}

Creating Instances

Create a struct instance using literal syntax with field names:

let p: Point = Point { x: 10, y: 20 }
let u: User = User { name: "Alice", age: 30, active: true }

Field Access & Assignment

Access fields with dot notation. Fields can be reassigned after creation:

let name: string = u.name  // field access
u.age = 31                 // field assignment
fmt.println(p.x)           // use in expressions

Struct Methods

Structs can have methods defined inside the struct body:

struct Point {
    x: int
    y: int

    fn sum(): int {
        return x + y
    }

    fn display(): void {
        fmt.println("Point(" + x + ", " + y + ")")
    }
}

let p = Point { x: 3, y: 4 }
let total: int = p.sum()  // 7
p.display()               // Point(3, 4)

A method receives the instance it was called on as a pointer, named self. Bare field names read through the receiver, so x and self.x mean the same thing when read — but assignment requires self, because a method's locals and its fields are separate namespaces.

fn moveTo(nx: int, ny: int): void {
    self.x = nx  // changes the instance
    self.y = ny
}

Fluent builders

Returning self from a method lets the next call in a chain continue from the same instance, so a builder reads as one expression:

struct Query {
    from: string
    max: int

    fn table(name: string): &Query {
        self.from = name
        return self
    }

    fn limit(n: int): &Query {
        self.max = n
        return self
    }
}

let q: Query = Query { from: "", max: 0 }
q.table("users").limit(25)
// q.from is "users", q.max is 25

The &Query return type is what says one instance is threaded through: nothing is copied per step. A chain may also start from a temporary, which is bound for the length of the statement and released at its end:

let sql: string = insertInto("users").col("id").col("email").text()

A chain's result can be bound as a reference with let r: &Counter = c.bump(). A method value such as q.sum still copies its receiver, so a mutating method reached that way changes the copy rather than the original.

Method chaining

More generally, a call is not the end of an expression. Its result can be indexed, have a field read, or have a method called on it:

let n: int = sb.toString().len()
let count: int = csv.split(",").len()
let third: string = csv.split(",")[2]
let size: int = csv.split(",")[2].len()
let shouted: string = "  mixed  ".trim().toUpper()

A string, array, map or StringBuilder is a receiver whether it is a named variable, a literal, or the result of the call before it. Each link's receiver is evaluated once and released if that link produced it, so csv.split(",")[2].len() splits once and frees the array at the end of the statement. A receiver that is simply a variable is used directly, with no temporary.

Field tags

A field may carry a tag: backtick-delimited metadata written after its type.

struct Book {
    id: long
    pages: int
    authorName: string `db:"COALESCE(a.name, '')"`
    releasedOn: string `db:"b.released_on::text"`
    priceMinor: long `db:"b.price_minor" json:"price"`
    note: string
}

The format is space-separated key:"value" pairs, so one field can carry several namespaces at once. A tag is raw — no escapes, no interpolation — which is what lets an SQL fragment like COALESCE(a.name, '') be written exactly as it will be used.

Tags are read back through reflect.fieldTag:

reflect.fieldTag(bk, 2, "db")    // "COALESCE(a.name, '')"
reflect.fieldTag(bk, 4, "json")  // "price"
reflect.fieldTag(bk, 0, "db")    // "" — that field has no tag

A tag is data, not a directive. The compiler stores it and never interprets it: nothing in the language knows what db or json means. That is the difference from an annotation — #[owned] changes what the compiler emits, so the valid set is closed and an unknown one is an error, whereas any tag key is allowed. (#[allow(...)] is the one exception: it suppresses a lint finding rather than directing the compiler, so it is accepted anywhere and checked by lint instead.) What the compiler does check is that the pairs are well formed, which catches the typo that would otherwise make a key silently invisible:

f: string `db:x`            // error: tag key 'db' must have a quoted value
f: string `db`              // error: tag key 'db' is missing its ':"value"'
f: string `db:"a" db:"b"`   // error: tag repeats key 'db'
f: string `db:"a"json:"b"`  // error: needs a space between keys

Any struct may carry tags — there is no separate kind of struct for it. The key is the discriminator: a type that means nothing to a database layer simply has no db key, and fieldTag reports "".

Value & Reference Semantics

Structs are pass-by-value by default. The function receives a copy — changes inside the function do not affect the caller:

fn tryUpdate(user: User): void {
    user.name = "changed"  // modifies the local copy only
}

let u = User { name: "john", age: 25 }
tryUpdate(u)
fmt.println(u.name)        // still "john"

Use &StructName in the parameter type to pass by reference. Mutations through the reference affect the original. The caller does not need to write & at the call site — the compiler inserts it automatically.

fn update(user: &User): void {
    user.name = "changed"  // modifies the original
}

let u = User { name: "john", age: 25 }
update(u)
fmt.println(u.name)        // "changed"

Primitives (int, long, double, bool, char) also support the & prefix for pass-by-reference:

}

fmt.println(x)  // 6

Interfaces

Interfaces define a contract — a set of method signatures that a type must have. DexLang uses structural typing: a struct satisfies an interface automatically if it has all the required methods with matching signatures. There is no implements keyword.

Defining an Interface

An interface lists method signatures only — no implementations, no fields:

interface Greeter {
    fn greet(): string
}

Satisfying an Interface

A struct satisfies an interface if it defines methods that match every signature. The matching is checked at compile time — no explicit declaration is needed:

interface Greeter {
    fn greet(): string
}

struct Person {
    name: string

    fn greet(): string {
        return "Hello, I'm " + name
    }
}

// Person satisfies Greeter because it has greet(): string

Using Interfaces as Types

An interface type can be a function parameter, a local, a return type, a struct field, or an array element. The parameter is the common case:

fn printGreeting(g: Greeter): void {
    fmt.println(g.greet())
}

let p = Person { name: "Alice" }
printGreeting(p)  // "Hello, I'm Alice"

An Interface Value Owns Its Data

An interface value is a refcounted box holding a copy of the struct it was built from, plus that struct's method table. Because it owns the copy rather than pointing at someone else's struct, it goes anywhere a value can go:

fn greeterFor(robot: bool): Greeter {
    let p = Person { name: "Eve" }
    return p                          // returned
}

struct Entry {
    key: string
    who: Greeter                      // stored in a field
}

let crowd: Greeter[] = [p, r]         // held in an array, mixed types
assert(crowd[0].greet() == "Hi Ada")  // dispatched through an element

Coercion costs one pooled allocation, and the struct's heap fields are retained rather than copied — a string in the original and a string in the box are the same bytes with one more reference.

The consequence of copying is that mutation through an interface does not reach the original:

let t = Tally { n: 0 }
let counts: Counter = t
assert(counts.bump(3) == 3)
assert(counts.total() == 3)
assert(t.n == 0)  // the box was mutated, not t

Go behaves the same way for the same reason. To mutate the original, call the method on the struct directly rather than through an interface.

Where an Interface Does Not Fit

Two containers refuse one, each for a reason of its own. A map holds only the six scalar value types — a struct value is refused identically — and an optional needs a spelling for absent, which a vtable pair does not have:

fn each(m: map[string, Greeter]): void {}  // compile error
fn maybe(g: Greeter?): void {}             // compile error

An array is the way to hold a varying number of them.

Multiple Methods

Interfaces can require multiple methods. All must be present with matching parameter and return types:

interface Shape {
    fn area(): double
    fn perimeter(): double
}

struct Circle {
    radius: double

    fn area(): double {
        return math.pi() * radius * radius
    }

    fn perimeter(): double {
        return 2.0 * math.pi() * radius
    }
}

// Circle satisfies Shape — both area() and perimeter() match

Compile-Time Checking

If a struct is missing a required method or the signature doesn't match, the compiler reports an error at the call site:

interface Stringer {
    fn toString(): string
}

struct Empty {
    x: int
}

fn show(s: Stringer): void {}

fn main(): void {
    let e = Empty { x: 1 }
    show(e)
}
argument 1 of 'show': expected Stringer, got Empty (missing fn toString(): string)

The error names what is absent rather than only that the types differ. A method present under the right name but the wrong signature is reported as a mismatch instead.

How It Works

Interfaces compile to C vtable structs. An interface value holds a pointer to the copy it owns, the refcounted box that copy lives in, and a table of function pointers. The compiler fills the table from the concrete struct type, which it knows at every coercion site, so all dispatch is resolved at compile time: one indirect call, no type metadata, no lookup. The box is released when the value goes out of scope, is overwritten, or is dropped by an exception unwinding past its frame.

Why no instanceof or typeof?

DexLang is statically typed. The compiler knows every variable's type at compile time, so there is no runtime type ambiguity to resolve. Languages that need instanceof typically have class inheritance hierarchies (Java, C#) where a parent-typed variable could hold different child types at runtime, or dynamic typing (JavaScript, Python) where types aren't known until execution. DexLang has neither — interfaces use structural typing resolved entirely at compile time.

Generics

A generic declaration takes type parameters in angle brackets. It is a template, not code: each distinct set of type arguments produces one concrete function or struct, named after them. There is no boxing, no type metadata, and no runtime dispatch — an instantiation is indistinguishable from the same code written out by hand.

Generic Functions

fn identity<T>(x: T): T {
    return x
}

fn pick<T>(a: T, b: T, first: bool): T {
    if (first) {
        return a
    }

    return b
}

Type arguments are inferred from the call, so a generic function is called like any other:

identity(42)      // T = int
identity("hi")    // T = string
pick(1, 2, true)  // T = int

Shared and Independent Type Parameters

Several parameters may share a type parameter, and they have to agree:

pick(1, "a", true)
pick() binds T to int from an earlier argument, but argument 2 is string

Type parameters are independent of one another:

fn describeTwo<A, B>(a: A, b: B): string {
    return "" + a + "/" + b
}

describeTwo(7, "s")  // A = int, B = string
describeTwo("s", 9)  // A = string, B = int

Inference Through Containers

Inference descends into a container, so the element type pins the parameter:

fn firstElem<T>(xs: T[]): T {
    return xs[0]
}

let nums: int[] = [10, 20]
firstElem(nums)  // T = int

A type parameter that appears in no parameter's type has nothing to be inferred from, and the compiler says so rather than guessing:

cannot infer type parameter T of makeDefault() from the arguments; it appears in no parameter's type

A generic may call a generic, including itself:

fn twice<T>(x: T): T {
    return identity(identity(x))
}

Generic Structs

struct Box<T> {
    value: T

    fn get(): T {
        return value
    }

    fn replace(v: T): T {
        self.value = v
        return self.value
    }
}

struct Pair<K, V> {
    key: K
    value: V
}

A struct's type arguments are written, not inferred — a struct type has no arguments to infer them from. Both the type and the literal name them:

let bi: Box<int> = Box<int> { value: 42 }
assert(bi.get() == 42)

let bs: Box<string> = Box<string> { value: "held" }
let pr: Pair<string, int> = Pair<string, int> { key: "a", value: 2 }

Two mentions of Box<int> are the same type, not two — the instantiation is built once and reused. Leaving the type arguments off names a template where a type is expected:

generic struct Box needs type arguments, as Box<...>

An instantiation is an ordinary struct, so everything that applies to one applies to it: a heap-typed field is owned and released the same way, methods work the same way, and it can be returned, nested, and held in an array.

fn boxed(n: int): Box<int> {
    return Box<int> { value: n }
}

let outer: Box<Box<int>> = Box<Box<int>> { value: inner }
let many: Box<int>[] = [inner, boxed(4)]

Declaration Order

A generic struct must be declared above the code that instantiates it, the same rule every type in DexLang follows.

Not Supported Yet

  • A user module cannot declare a generic. The template lives in the parser that read it, and instantiating one needs that parser; a generic struct is harder still, because its instantiation happens while a file is parsed and a module is read after the main program already was. Declaring one is a clear error rather than a silent omission.
  • No type parameter bounds. fn show<T: Stringer>(x: T) does not parse. A generic body may only do what every type supports, so an operation the type argument does not have is reported against the instantiation.
  • A generic struct cannot appear in a generic signature. fn unwrap<T>(b: Box<T>): T is not supported: inference would have to match a type argument structurally through an instantiation.

How It Works

Generics are monomorphised by re-parsing. A generic declaration is captured as the tokens it was written as and skipped rather than parsed; instantiating it re-parses those tokens with its type parameters bound to concrete types and its own name mangled to Box_int or max_int. What comes out is an ordinary function or struct, which is why the code generator needs no knowledge of generics at all.

A struct's instantiation happens in the parser, where the type arguments are written. A function's happens in the type checker, because inferring them needs the argument types and only the checker has those; the checker asks the parser to re-parse, registers the result, and appends it to the program, where the body-checking pass reaches it like any other function.

Modules & dex.mod

A project that shares code with other projects has a dex.mod at its root. It names the project by its URL and lists the libraries it uses. Create one with dex mod init and add libraries with dex get; a project without one works exactly as before.

dex mod init github.com/acme/web
dex get github.com/acme/greet
module github.com/acme/web

require github.com/acme/greet v0.1.0

Imports

An import whose first segment looks like a host name names a module; anything else is a file relative to the importing one.

import "service/users"                      // beside this file
import "github.com/acme/web/service/users"  // the same file, from anywhere in the project
import "github.com/acme/greet"              // a library: greet.dx at its root
import "github.com/acme/greet/internal/shout"

require and replace

require names a library and the version used — a git tag its author pushed. replace says where to read it from instead of downloading it: a folder on your machine, written ./dir or ../dir relative to the dex.mod. That is how a monorepo works, and how you change a library alongside the program using it. Delete the replace once the library is published and the same imports read the downloaded copy.

dex get

dex get github.com/acme/greet              # the latest release
dex get github.com/acme/greet@v1.2.0       # that release
dex mod download                           # everything dex.mod requires, for CI and Docker
dex mod verify                             # check the cache against dex.sum

A release is a git tag: v1.2.0 for a library at the root of its repository, or redis/v0.1.0 for one in a redis folder of a repository that holds several modules. dex get downloads the release into the module cache (~/.dex/pkg/mod, or DEX_MODCACHE), writes the require line, fetches what the library itself requires, and records a checksum in dex.sum — commit it. A release that changes after it was first downloaded fails with both checksums named.

A build never downloads: a required module missing from the cache is an error at its import that says to run dex mod download. Fetching uses git, so a private repository works wherever git clone of it does.

Calling C

An external module block declares C functions, the headers they need, and the libraries to link against. The block is the declaration, so there is no import, and a call compiles to a direct call to the C symbol with no wrapper:

external module zlib {
    include "<zlib.h>"
    link "-lz"

    fn compressBound(sourceLen: long): long
    fn compileFlags(): long = "zlibCompileFlags"
}

fn main(): void {
    fmt.println(zlib.compressBound(1024))  // 1037
}

= "symbol" names a C function whose own name reads badly in Dex. int, long, double, bool, char and string cross the boundary, plus void as a return type and opaque handles.

Out-Parameters

A C function that returns a result through a pointer argument takes it as an & parameter. The caller passes a variable and C writes into it; null skips the output. Scalars and handles can be written.

fn open(path: string, db: &Db?): int = "sqlite3_open"

let db: Db? = null
let rc: int = sq.open("app.db", db)

Decode base64. Binary-safe: the result may contain NUL bytes.

Base64-encode a string. Binary-safe: NUL bytes are encoded, not truncated.

Decode base64url (RFC 4648 §5) — the '-' and '_' alphabet JWTs are written in, with padding optional. Binary-safe. base64Decode skips those two characters instead of decoding them, so a token decoded with it comes back the wrong length.

crypto.bcryptHash(password: string, cost: int) -> string

Hash a password with bcrypt at a cost from 4 to 31 (10 is common), as $2b$<cost>$<salt><hash>, for systems whose stored hashes are already bcrypt. "" for a cost out of range, a password containing a NUL byte, or a build without libxcrypt. bcrypt reads only the first 72 bytes of a password. New systems should prefer hashPassword.

crypto.bcryptVerify(password: string, stored: string) -> bool

Whether a password matches a bcrypt hash ($2a$, $2b$ or $2y$), compared in constant time. False for a malformed hash, a password containing a NUL byte, and without libxcrypt.

crypto.bcryptVerifyAll(passwords: string[], stored: string[]) -> bool[]

bcryptVerify for each passwords[i] against stored[i], computed side by side: four passwords take about 1.5 times as long as one, so a batch of logins costs well under half the CPU per password. The same answers as bcryptVerify, which handles any pair this cannot (passwords with bytes over 127 among them). One bool per password; false where stored has no entry.

crypto.decrypt(keyHex: string, sealed: string) -> string

Decrypt what encrypt produced. Returns "" for a wrong key or input that was altered or cut short. Binary-safe. Needs OpenSSL.

crypto.encrypt(keyHex: string, plaintext: string) -> string

Encrypt a secret for storing: AES-256-GCM with a fresh nonce, as base64. The key is 32 bytes as 64 hex digits, from randomHex(32). Returns "" for a bad key. Needs OpenSSL.

crypto.hashPassword(password: string) -> string

Hash a password for storing: PBKDF2-HMAC-SHA-256, a random salt, 600000 iterations, as pbkdf2-sha256$<iterations>$<salt>$<hash>. Needs OpenSSL.

crypto.hmacSha1Hex(key: string, message: string) -> string

HMAC-SHA-1, as lowercase hex. Only for protocols that require it, such as TOTP; prefer hmacSha256Hex otherwise. Needs OpenSSL.

crypto.hmacSha256B64Url(key: string, message: string) -> string

HMAC-SHA-256, as unpadded base64url. The encoding a JWS signature is written in, so an HS256 token's third segment compares against this directly — no decoding on the verify path. Compare with crypto.secureEquals. Needs OpenSSL.

crypto.hmacSha256Hex(key: string, message: string) -> string

HMAC-SHA-256, as lowercase hex. Needs OpenSSL.

crypto.hmacSha512Hex(key: string, message: string) -> string

HMAC-SHA512 of a message under a key, as lowercase hex. What Paystack signs webhooks with.

crypto.randomBase32(bytes: int) -> string

http

http.afterBatch(hook: fn(): bool) -> void

Run hook, a fn(): bool, after a batch of handlers and before any of their responses is sent, so handlers can share one database transaction and have it committed before a client hears its request succeeded (group commit). Return true when the batch's work is durable; return false and every request in the batch is answered 500 {"error":"internal server error"} instead of what its handler returned. Under http.uring() a batch is every request one pass of the event loop served, which under load is many; with http.inline() or the thread pool it is a single request, so the guarantee holds everywhere but only io_uring batches. On the thread pool the hook runs on the worker that ran the handler. Registering twice replaces the first.

http.batchWindow(ms: int) -> void

Under http.uring(), keep a batch open until its first request has waited ms milliseconds (or 4,096 requests have joined), so the http.afterBatch hook serves more requests per run: what one query answers for all of them costs the database less per request. Every response in the batch waits for the hook, so this adds up to ms to each one's latency. 0, the default, closes a batch after every pass of the loop; at most 1000. Call before listen. Other backends run the hook per request and ignore it.

Also serve the same routes on another port of the same host. Call before listen; up to three extra ports. Each listening address takes its own share of client connections, which matters past the roughly 64,000 connections one client address can open to one port.

Split the program into count processes that will share one listening port, and return this process's index: 0 in the original, 1 to count-1 in the copies. 0 means one per CPU. Call it before opening anything a process must own alone, such as a database connection, then open those and call listen with one worker. The copies receive SIGTERM when the original exits. A second call returns the same index without forking again.

Under http.uring(), when the last pass of the event loop had work, sleep until count completions have arrived or micros microseconds have passed before running the next pass, instead of waking for each one. Each pass then serves more requests with one round of system calls and one http.afterBatch run, which under load costs less CPU per request; each response can wait up to micros longer. Idle, the loop still wakes for the first event. 0 (the default) turns it off; count is at most 4096 and micros at most 100000. Needs Linux 5.11 or later; older kernels ignore it. Call before listen.

Take a ticket for the request this handler is serving, so the http.afterBatch hook can answer it with http.reply. Handlers collect their batch's work, the hook runs it as one query, and replies to each ticket before any response is sent. Returns -1 when there is no hook, when called outside a handler or a second time for the same request; answer from the handler then. A request the hook does not reply to is sent what its handler returned, so return a fallback such as a 500.

http.inline() -> void

Run every handler on the thread that owns the sockets instead of handing it to the pool. Call before listen. Each request then costs no thread handoff, lock or wakeup, and its response is written straight away, which is the fastest choice on one core when handlers are short and only touch local state such as an SQLite file. Handlers run one at a time, so a handler that blocks, on an outbound request or a sleep, stalls every connection while it does.

http.lanes(count: int, serve: fn(lane: int, payloads: string[]): void) -> void

Start count lane processes (1 to 16) that answer requests handlers pass on with http.relay. A lane gathers what every worker relays to it and calls serve, a fn(lane: int, payloads: string[]): void, with the whole batch, so one query can answer requests from every worker at once instead of a few from each. serve answers payloads[i] with http.reply(i, ...); one it leaves unanswered gets 500. A lane is its own process: it opens what it needs, such as its database connection, itself, and the batch it is serving waits on nothing else. While a lane is busy, the next batch gathers; with http.batchWindow set before this call, a batch also stays open until its first request has waited that long. Call before http.fork and listen, on Linux; elsewhere it does nothing and http.relay returns false.

http.later() -> bool

Under uring, run the handler serving this request again on the next pass of the loop instead of answering now; what it returns this time is discarded. For work that cannot proceed yet without blocking the loop, such as a write while another connection holds the database's write lock. Returns false outside a handler, on other backends, after a second call in the same run, or once the request has been waiting 1 second; answer from the handler then.

http.limits(maxBodyBytes: int, idleTimeoutSecs: int, maxConnections: int) -> void

Bound what one client can cost the server. Call before listen. Defaults are 8 MB, 30 seconds and 8192 connections; a 0 for any argument keeps that default, so raising the body limit for uploads does not mean restating the others. The header block is capped at 32 KB and is not adjustable. A body larger than the limit is answered 413, headers that never terminate 431, and a connection that stops making progress for the idle timeout is closed. The connection limit is also held below the process's open-file limit. Past fifteen sixteenths of it, responses carry Connection: close so idle clients reconnect for their next request, and at the limit new connections wait in the listen queue until one closes.

http.uring() -> void

Serve with io_uring instead of epoll, on Linux. Call before listen. Database

The db module provides a unified interface for SQLite, PostgreSQL, MySQL, and MongoDB. The API follows a handle-based pattern: open a connection, execute statements or query rows, iterate with a cursor, and clean up.

import "db"

let conn: int = db.open("sqlite", "app.db")
db.exec(conn, "CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, name TEXT)")
db.exec(conn, "INSERT INTO users (name) VALUES ('Alice')")

let rows: int = db.query(conn, "SELECT id, name FROM users")
while (db.next(rows)) {
    let name: string = db.col(rows, 1)
    fmt.println(name)
}

db.free(rows)
db.close(conn)

Concurrency

DexLang provides lightweight concurrency with four primitives: spawn, send, receive, and channel. Under the hood these compile to a fixed-size thread pool (backed by pthreads) and a lock-free channel implementation.

spawn

Launch a concurrent task. Returns a task handle that can be used with receive to get results.

Block form

Run arbitrary code in a new thread. Use send(value) to return a result to the caller.

let task = spawn {
    let result = expensiveComputation()
    send(result)
}

let val = receive(task)

Function call form

Spawn a single function call. The function's return value is automatically sent back.

fn compute(n: int): int {
    return n * 2
}

let task = spawn compute(21)
let val = receive(task)  // 42

Fire-and-forget

If you don't need the result, omit the assignment. The task runs in the background.

spawn {
    doBackgroundWork()
}

send

Send a value from inside a spawn block, or to a shared channel. Inside a spawn block, send(value) delivers the value to whoever calls receive(task). With two arguments, send(channel, value) pushes a value into a shared channel for many-to-one communication.

send(value)           // send to the task's implicit handle
send(channel, value)  // send to a shared channel

receive

Block until a value is available from a task handle or channel, then return it. The return type matches the type that was sent. For task handles, this is determined by the send(value) call or the spawned function's return type.

let val: int = receive(task)     // receive from a task handle
let val: int = receive(channel)  // receive from a channel

channel

Create a shared channel for many-to-one communication. Takes a type argument specifying the element type. Channels are typed — a channel(int) can only carry int values.

let ch = channel(int)
let ch: chan int = channel(int)  // explicit type annotation

close

Close a channel. Subsequent sends are ignored and blocked receivers get zero values.

close(ch)

Patterns

1-to-1 (task sends result to parent)

A single spawned task sends its result back to the parent via send/receive:

let task = spawn {
    send(42)
}

assert(receive(task) == 42)

Many-to-one (fan-in via shared channel)

Multiple tasks push values into a shared channel, and the parent collects them:

let ch = channel(int)
for (let i = 0; i < 10; i++) {
    spawn {
        send(ch, i * 10)
    }
}

let total = 0
for (let i = 0; i < 10; i++) {
    total += receive(ch)
}

Variable capture

Spawn blocks automatically capture variables from the outer scope by value. Mutations inside the block do not affect the original variables.

let x: int = 10
let task = spawn {
    // x is captured by value — this is a copy
    send(x * 2)
}

let result = receive(task)  // 20

Mutex

Channels pass values between threads. When threads instead need to share the same data, guard it with a mutex. Write mutex in value position to create one, already unlocked. It has two methods: .lock() and .unlock().

let mu: mutex = mutex
mu.lock()
// critical section — only one thread at a time
mu.unlock()

Module-level state needs a lock

Module-level variables are shared by every thread, and maps and arrays are not internally synchronised — two threads writing one at the same time can corrupt it, not merely lose an update. A map that resizes while another thread reads it will follow freed memory.

let mu: mutex = mutex
let totals: map[int, int] = {}

fn record(key: int, amount: int): void {
    mu.lock()
    totals.set(key, amount)
    mu.unlock()
}

fn lookup(key: int): int {
    mu.lock()
    let found: int = -1
    if (totals.has(key)) {
        found = totals.get(key)
    }

    mu.unlock()  // unlock before returning, not after
    return found
}

Note the shape of lookup: read what you need into a local, unlock, then return. Returning from inside the critical section would skip the unlock and deadlock every other thread.

Hold a lock for as little as possible, and avoid doing I/O — a database call, a socket write — while holding one, since every other thread waits on you. Take the value you need under the lock, release it, then do the slow work.

Protecting shared state

A mutex can also live in a struct, which keeps the lock next to the data it protects — useful when you pass state to threads by reference rather than reaching for a module-level variable. Without a mutex, concurrent writes cause data races:

struct Counter {
    mu: mutex
    value: int
}

fn increment(c: &Counter): void {
    c.mu.lock()
    c.value = c.value + 1
    c.mu.unlock()
}

fn main(): void {
    let c = Counter { mu: mutex, value: 0 }
    let ch = channel(int)

    for (let i = 0; i < 10; i++) {
        spawn {
            increment(c)
            send(ch, 1)
        }
    }

    // Wait for all 10 threads to finish
    for (let i = 0; i < 10; i++) {
        receive(ch)
    }

    assert(c.value == 10)
}

Safe unlock with defer

If code inside a lock can throw an exception, a bare .unlock() call may never execute — leaving the mutex locked and all other threads deadlocked. Use defer to guarantee the unlock runs on both normal return and exception:

fn increment(c: &Counter): void {
    c.mu.lock()
    defer c.mu.unlock()  // runs when function exits, no matter what

    riskyOperation()     // if this throws, defer still fires
    c.value = c.value + 1
}

defer queues a call that executes when the function exits — whether by return, by falling off the end, or because an exception unwound past the frame. Multiple defers run in LIFO order (last defer runs first).

The call is registered when the defer statement runs: one inside a branch that was not taken registers nothing, and one inside a loop registers per iteration. What the call needs is captured where the defer is written, so it still works after the frame it came from is gone — which also means its arguments are evaluated at the defer rather than at the exit.

Safe unlock with try/finally

Alternatively, use try/finally for block-scoped cleanup:

fn increment(c: &Counter): void {
    c.mu.lock()
    try {
        riskyOperation()
        c.value = c.value + 1
    } catch (e: Exception) {
        fmt.println("Error: " + e.message)
    } finally {
        c.mu.unlock()  // always runs
    }
}

Threading Model

Each spawn submits work to a fixed-size thread pool that is initialized at program start. The pool size is automatically set to the number of CPU cores, clamped between 4 and 16 threads. Worker threads are reused across spawns, so there is no per-spawn thread creation overhead.

When to use spawn

Spawn is well-suited for parallelism at any scale: splitting CPU-bound work across cores, running background tasks, or fan-out/fan-in patterns. The thread pool ensures that even thousands of spawns remain efficient, with tasks queued and dispatched to the fixed set of worker threads.

Error Handling

DexLang provides structured exception handling with try, catch, finally and throw. Exceptions carry a type, so a signature can say what escapes it and a handler can choose which kind it takes.

Exception Type

Exception is the built-in exception type, a struct with a single field:

// Built-in (always available, no import needed)
// struct Exception(message: string) {
//     message: string
// }

Throwable Types

Any struct can be thrown when it carries a message: string and nothing that would need releasing:

struct ParseError(message: string, line: int) {}       // throwable
struct IOError(message: string) {}                     // throwable
struct Plain(code: int) {}                             // no message field
struct TwoStrings(message: string, detail: string) {}  // detail cannot survive

The restriction comes from the unwind. A throw is a longjmp, so the message is copied into the runtime before the jump and the remaining fields travel as a flat byte copy. An int, bool, double or char survives that; a second string could only arrive already freed, so the compiler refuses it rather than hand you a dangling one.

Throwing Exceptions

Use throw to raise an exception with a message:

throw Exception("something went wrong")
throw ParseError("not a digit", 12)

Declaring That a Function Throws

A throws after the return type says an exception may escape, so a caller sees it in the signature rather than discovering it at runtime. Naming types after it says which:

fn load(path: string): int throws ParseError, IOError {
    if (path == "") {
        throw IOError("no path")
    }

    throw ParseError("bad digit", 12)
}

// something escapes, unspecified
fn anything(): int throws {
    throw Exception("whatever")
}

The declaration is checked against what the function does by dex lint rather than by the compiler — the program runs either way. Lint reports an exception that escapes a function not declaring it, a type a throws list leaves out, and a throws naming a type the function cannot throw. Throwing is inferred transitively; a throw inside a lambda or a spawn does not escape the function that wrote it, because it runs in another frame or on another thread.

Try-Catch-Finally

Use try to wrap code that may throw, catch to handle exceptions, and finally for cleanup that always runs:

import "fmt"

fn main(): void {
    try {
        throw Exception("oops")
    } catch (e: Exception) {
        fmt.println(e.message)  // "oops"
    } finally {
        fmt.println("cleanup")
    }
}

Catching by Type

A try may have any number of catch clauses. The first whose type matches the thrown one runs, and reads that type's own fields:

try {
    let n = load(path)
    fmt.println("n=${n}")
} catch (e: ParseError) {
    fmt.println("line ${e.line}: ${e.message}")
} catch (e: IOError) {
    fmt.println("io: ${e.message}")
}

catch (e: Exception) is the catch-all — it handles every type, which is what a single catch clause always did. A clause after it can never run, and lint reports that. A catch-all handling some other type sees that type's message and zeroes for anything else.

An exception no clause matches carries on outward, after this try's finally has run, with its message and fields intact. The heap values the skipped frames held are released and their deferred calls run, so throwing on an error path neither accumulates memory nor skips cleanup.

Try-Finally (No Catch)

If only finally is used without catch, the exception is re-thrown after the finally block runs:

try {
    throw Exception("error")
} finally {
    fmt.println("always runs")
}

// exception propagates after finally

Cross-Function Exceptions

Exceptions propagate through function calls:

fn risky(): void {
    throw Exception("from risky")
}

fn main(): void {
    try {
        risky()
    } catch (e: Exception) {
        fmt.println(e.message)  // "from risky"
    }
}

Unhandled Exceptions

If an exception is not caught, the program prints Unhandled <Type>: <message> to stderr and exits with code 1.

Module-Scoped Types

A type declared in a user module belongs to that module, the way a function does. Two modules can each declare a Response, and they are two types:

// model/charging.dx
struct Response(ok: bool) {}

// model/billing.dx
struct Response(code: int) {}
import "model/charging"
import "model/billing"

let a: charging.Response = charging.make()
let b: billing.Response = billing.make(404)

How a Reference Resolves

  1. Qualified — charging.Response always names that module's type.
  2. Its own module's — inside charging, a bare Response is charging's, even if an import declares one too. The same rule a function follows: inside a module you call make(), not charging.make().
  3. Unqualified, one declarer — a bare Response resolves when exactly one module in scope declares it, which is why existing code needs no changes.
  4. Unqualified, several declarers — an error naming them.
app.dx:6:21: ambiguous type 'Response': declared by 'charging.Response'
and 'billing.Response' — qualify it, as in charging.Response

Diagnostics and editor hovers show the qualified spelling, so a type reads the way it was written rather than by the flat name it registers under. The struct types a stdlib module provides — http.HttpRequest, ws.Conn — are not module-scoped and keep working under either spelling.

Linting

dex lint reports what compiles but is probably not what was meant: a binding nothing reads, a statement nothing reaches, an exception nothing handles. Building reports it by default, and it never changes what is emitted.

dex build app.dx                # build and report findings
dex build app.dx --no-lint      # build without them
dex build app.dx --lint=strict  # ... fail the build if anything is reported
dex lint app.dx                 # front end only: no C generated, no cc run
dex lint --rules                # list the rules and what each one finds
dex build app.dx --lint-off=unused-param,shadow

The language server reports the same findings as you type, graded by whether something is actually wrong. A warning is for a throws the body contradicts, a catch that can never run, code nothing reaches, or an #[allow(...)] naming no rule. Everything else is a hint — a quiet grey mark rather than a squiggle.

uncaught-throw is a hint for that reason. An editor asks for every diagnostic on every keystroke; since throws is an optional declaration, every throw in a codebase that has not adopted it would otherwise be underlined as though it were broken.

Struct Size and Field Order

The compiler lays a struct out with its widest fields first, so the order you declare fields in never costs padding: struct Reading { ok: bool, at: long, stale: bool } is 16 bytes, laid out as at, ok, stale, where declared order would be 24. Everything you can observe keeps declared order (struct literals, auto-constructor parameters, json.encode, printing, reflect field indexes and db.fill); only the memory layout changes. A standard library struct keeps its declared layout, which its C runtime relies on.

Hovering a struct's name shows its size, alignment and padding, and when the layout differs from declared order, the order used and what declared order would have cost. struct-padding reports that difference as a finding, a hint in the editor; #[allow(struct-padding)] on the struct keeps an order chosen for another reason. Sizes are for a 64-bit target.

Suppressing a Finding

#[allow(<rule>)] on the declaration it fires on silences one rule there. #[allow(unused)] covers the four unused-* rules and #[allow(all)] covers everything:

#[allow(unused)]
let reserved = buildHandle()   // kept for its side effect, never read

An #[allow(...)] is the one annotation the compiler does not interpret: it says what not to report, so it is accepted on any type rather than only on the heap types #[owned] is restricted to. A rule name it does not recognise is itself a finding, because a suppression that silences nothing reads as handled and behaves as forgotten.

Where an Escaping Exception Is Reported

Throwing is inferred exactly, but a finding follows a declaration rather than the inference:

  • An undeclared throw is reported where it is raised — once per type, at the one place that can fix it.
  • Writing throws there is what tells its callers. A call to a function that declares it, unguarded and in a caller that does not declare it either, is the caller's finding; declaring it there moves the obligation one step further out, until something catches it.

That is the gradient Java gets from making the declaration mandatory, reached by making the obligation follow the annotation instead. It also means a throw used as an assertion stays one finding. Measured on a 211-file codebase: a single guard in a shared query builder was reachable from 500 unguarded call sites, and reporting each of them said nothing a reader could act on, because the decision about where to catch is made once rather than 500 times.

What It Does Not Do

  • Assignment is not use. A variable only ever written to is reported as unused, which is the point — let total = 0 followed by total += n and nothing else is dead arithmetic.
  • A bare return ends its block. return with no value takes the next expression as its value, so nothing survives after it to be called unreachable. The rule fires after return <value>, throw, break and continue.
  • A module that declares types is never reported unused. import "json" earns its keep through a json.Value annotation, and a type annotation is resolved while parsing — by the time lint runs there is no mention of the module left to find. Only function-only modules such as str and math are checked.
  • A call through a function value is assumed not to throw. Which function a closure holds is a runtime fact, so the throw inference stops there rather than guessing.

The json module is two functions — encode and decode — plus one type, json.Value. Use a struct when the shape is known at compile time, and json.Value for a document you want to index and walk.

Production settings

Settings that bound what a client can cost the server, and give it a proper 404 and compressed responses. Call each before listen.

http.limits(maxBodyBytes: int, idleTimeoutSecs: int, maxConnections: int) -> void

Bound what one client can cost the server. Call before listen. Defaults are 8 MB, 30 seconds and 8192 connections; a 0 for any argument keeps that default, so raising the body limit for uploads does not mean restating the others. The header block is capped at 32 KB and is not adjustable. A body larger than the limit is answered 413, headers that never terminate 431, and a connection that stops making progress for the idle timeout is closed. The connection limit is also held below the process's open-file limit. Past fifteen sixteenths of it, responses carry Connection: close so idle clients reconnect for their next request, and at the limit new connections wait in the listen queue until one closes.

http.notFound(handler: fn) -> void

Answer requests no route matched. The handler takes the same shapes http.route() accepts, so a program can give its 404 its own body and content type instead of the built-in one. Registering twice replaces the first.

http.responseWith(statusCode: int, body: string, contentType: string, headers: string) -> HttpResponse

Create an HttpResponse carrying extra headers, newline-separated "Key: Value" pairs as built by http.header(). Use for Set-Cookie (which may repeat) and the Access-Control-* family.

http.gzip(minBytes: int) -> void

Compress 2xx response bodies of at least minBytes with gzip for clients whose Accept-Encoding allows it, adding Content-Encoding: gzip and Vary: Accept-Encoding. A body that would not get smaller is sent as it is. Handlers return plain bodies either way. Uses libdeflate at its fastest level when it is installed at build time (libdeflate-dev on Debian and Ubuntu); without it this does nothing. 0, the default, is off. Call before listen.

http.listenOn(host: string, port: int, [workers: int]) -> void

Start the HTTP server bound to one interface. http.listen() binds every interface; this one names the address, for a service behind a proxy that should not also be reachable directly. The host must be an IPv4 address — "127.0.0.1", or "0.0.0.0" for every interface. Optional third argument is the worker process count (0 = one per CPU).

http.extraPort(port: int) -> void

Also serve the same routes on another port of the same host. Call before listen; up to three extra ports. Each listening address takes its own share of client connections, which matters past the roughly 64,000 connections one client address can open to one port.

Calling other services

The plain client functions above use default timeouts and follow no redirects. For a host you do not control, set them explicitly with HttpOptions, and use the streaming forms for a large body or a model API's server-sent events.

http.requestWith(method: string, url: string, body: string, headers: string, options: HttpOptions) -> HttpResponse

Send a request under explicit HttpOptions: timeouts, redirect following, and TLS verification. Use it for any host you do not control.

http.stream(method: string, url: string, body: string, headers: string, options: HttpOptions, onChunk: fn(string): bool) -> HttpResponse

Send a request and hand a 2xx body to onChunk, a fn(string): bool, piece by piece as it arrives; return false from it to stop reading. Returns the HttpResponse with an empty body once the stream ends, or with the whole body for any other status, which is not streamed. Status 0 means the stream did not finish, with the reason in the body. A throw from onChunk aborts the request and is rethrown from here. options.timeoutMs bounds the whole stream.

http.streamEvents(method: string, url: string, body: string, headers: string, options: HttpOptions, onEvent: fn(string): bool) -> HttpResponse

http.stream for a text/event-stream body: onEvent is handed the data of each server-sent event, its data lines joined by newlines, whatever way the bytes were split on the wire. Comments, event names, ids and events with no data are skipped. This is how model APIs stream a reply.

The server has three ways of running handlers. Pick one before listen; the handlers themselves are the same code in all three.

http.threads(count: int) -> void

How many threads run handlers. Call before listen. 0, the default, sizes the pool from the CPU count with a floor of four — the right hedge when a handler might block on a database or an outbound request. Set it lower when handlers are CPU-bound and serialised behind a lock on a small box, where extra threads only add context switches to work that cannot overlap.

http.inline() -> void

Run every handler on the thread that owns the sockets instead of handing it to the pool. Call before listen. Each request then costs no thread handoff, lock or wakeup, and its response is written straight away, which is the fastest choice on one core when handlers are short and only touch local state such as an SQLite file. Handlers run one at a time, so a handler that blocks, on an outbound request or a sleep, stalls every connection while it does.

io_uring

On Linux, http.uring() replaces epoll with io_uring. Accepts, reads, writes and closes are queued on one ring and submitted together, so a pass of the event loop costs one system call however many connections it served. On macOS, on a kernel without io_uring, or in a container that blocks it, the server says so at startup and falls back to epoll, so the same program runs everywhere.

Each pass of the loop is a batch: every request that pass served. That is what makes the batching functions below worth having. Under load a batch holds many requests, and one database transaction or one query can serve all of them.

http.uring() -> void

Serve with io_uring instead of epoll, on Linux. Call before listen. Accepts, reads, writes and closes are queued on one ring and submitted together, so a pass of the loop costs one system call however many connections it served. Handlers run on the thread that owns the ring, as with http.inline(). Where io_uring is unavailable — another platform, an older kernel, or a container that blocks it — the server says so and uses epoll. Received bytes land in buffers the ring shares, so a connection waiting on its client holds no read buffer. When http.limits asks for more connections than one ring can hold (a ring is capped at the open-file limit), the server runs several rings on the same thread, up to eight.

http.gather(count: int, micros: int) -> void

Under http.uring(), when the last pass of the event loop had work, sleep until count completions have arrived or micros microseconds have passed before running the next pass, instead of waking for each one. Each pass then serves more requests with one round of system calls and one http.afterBatch run, which under load costs less CPU per request; each response can wait up to micros longer. Idle, the loop still wakes for the first event. 0 (the default) turns it off; count is at most 4096 and micros at most 100000. Needs Linux 5.11 or later; older kernels ignore it. Call before listen.

http.later() -> bool

Under uring, run the handler serving this request again on the next pass of the loop instead of answering now; what it returns this time is discarded. For work that cannot proceed yet without blocking the loop, such as a write while another connection holds the database's write lock. Returns false outside a handler, on other backends, after a second call in the same run, or once the request has been waiting 1 second; answer from the handler then.

gather makes batches bigger by waiting briefly before each pass, and later lets a handler step aside when it would otherwise block the loop, for example while another connection holds SQLite's write lock. A typical io_uring setup:

http.afterBatch(commitBatch)
http.uring()
http.gather(64, 250)        // wait for 64 completions or 250 µs
http.limits(0, 75, 200000)  // keep the default body limit
http.listenOn("0.0.0.0", 80, 1)

Batching and group commit

A durable write costs a disk flush, and a flush costs the same for one row as for a thousand. http.afterBatch runs a hook after a batch of handlers and before any of their responses is sent, so the handlers in a batch can share one transaction and the hook commits it once. Every client still hears "saved" only after its write is on disk.

import "db"
import "http"

let conn: int = -1
let insert: int = -1
let inTx: bool = false

fn createNote(req: http.HttpRequest): http.HttpResponse {
    if (!inTx) {
        db.exec(conn, "BEGIN IMMEDIATE")
        inTx = true
    }

    db.bindStr(insert, 1, req.body)
    db.step(insert)
    db.reset(insert)
    return http.response(201, "{\"saved\":true}", "application/json")
}

fn commitBatch(): bool {
    if (!inTx) {
        return true
    }

    inTx = false
    return db.exec(conn, "COMMIT") >= 0
}

fn main(): void {
    conn = db.open("sqlite", "notes.db")
    db.exec(conn, "PRAGMA journal_mode=WAL")
    db.exec(conn, "CREATE TABLE IF NOT EXISTS notes(body TEXT)")
    insert = db.prepare(conn, "INSERT INTO notes(body) VALUES (?)")

    http.route("POST", "/notes", createNote)
    http.afterBatch(commitBatch)
    http.uring()
    http.gather(64, 250)
    http.listen(8080, 1)
}

If the hook returns false, every request in the batch is answered 500 instead of what its handler returned, so no client is told a write succeeded when it did not. Under the thread pool or inline mode a batch is a single request, so the same program is correct there too; it just doesn't batch.

    let ticket: int = http.hold()
    if (ticket < 0) {
        return http.response(200, lookupOne(req.params.get("id")), "application/json")
    }

    tickets.push(ticket)
    ids.push(req.params.get("id"))
    return http.response(500, "{\"error\":\"not answered\"}", "application/json")
}

fn answerBatch(): bool {
    foreach (tickets as i, ticket) {
        http.reply(ticket, 200, lookupOne(ids[i]), "")
    }

    tickets = []
    ids = []
    return true
}
http.afterBatch(hook: fn(): bool) -> void

Run hook, a fn(): bool, after a batch of handlers and before any of their responses is sent, so handlers can share one database transaction and have it committed before a client hears its request succeeded (group commit). Return true when the batch's work is durable; return false and every request in the batch is answered 500 {"error":"internal server error"} instead of what its handler returned. Under http.uring() a batch is every request one pass of the event loop served, which under load is many; with http.inline() or the thread pool it is a single request, so the guarantee holds everywhere but only io_uring batches. On the thread pool the hook runs on the worker that ran the handler. Registering twice replaces the first.

http.hold() -> int

Take a ticket for the request this handler is serving, so the http.afterBatch hook can answer it with http.reply. Handlers collect their batch's work, the hook runs it as one query, and replies to each ticket before any response is sent. Returns -1 when there is no hook, when called outside a handler or a second time for the same request; answer from the handler then. A request the hook does not reply to is sent what its handler returned, so return a fallback such as a 500.

http.reply(ticket: int, statusCode: int, body: string, contentType: string) -> void

Answer a request http.hold took a ticket for, from the http.afterBatch hook of the batch that took it. An empty contentType means application/json. A ticket from another batch, one already answered, or a call outside the hook is ignored.

http.batchWindow(ms: int) -> void

Under http.uring(), keep a batch open until its first request has waited ms milliseconds (or 4,096 requests have joined), so the http.afterBatch hook serves more requests per run: what one query answers for all of them costs the database less per request. Every response in the batch waits for the hook, so this adds up to ms to each one's latency. 0, the default, closes a batch after every pass of the loop; at most 1000. Call before listen. Other backends run the hook per request and ignore it.

Using every core

One io_uring or inline server runs handlers on one thread. To use more cores, run several copies of the process sharing one port: http.listen(port, workers) does it for you, and http.fork does it earlier, so each copy can open its own database connection after the split.

http.fork(count: int) -> int

Split the program into count processes that will share one listening port, and return this process's index: 0 in the original, 1 to count-1 in the copies. 0 means one per CPU. Call it before opening anything a process must own alone, such as a database connection, then open those and call listen with one worker. The copies receive SIGTERM when the original exits. A second call returns the same index without forking again.

When several processes write one SQLite file, each takes the write lock in turn. Lanes avoid that: a lane is a separate process that owns the database, and every worker passes its requests to it with http.relay. The lane gets the requests from all workers together and can answer them with one query.

fn serve(lane: int, payloads: string[]): void {
    foreach (payloads as i, id) {
        http.reply(i, 200, json.encode({ id: id, lane: lane }), "")
    }
}

fn lookup(req: http.HttpRequest): http.HttpResponse {
    if (http.relay(0, req.params.get("id"))) {
        return http.response(500, "", "")
    }

    return http.response(503, "{\"error\":\"no lane\"}", "application/json")
}

fn main(): void {
    http.lanes(1, serve)
    http.fork(0)
    http.route("GET", "/item/:id", lookup)
    http.uring()
    http.listen(8080, 1)
}
http.lanes(count: int, serve: fn(lane: int, payloads: string[]): void) -> void

Start count lane processes (1 to 16) that answer requests handlers pass on with http.relay. A lane gathers what every worker relays to it and calls serve, a fn(lane: int, payloads: string[]): void, with the whole batch, so one query can answer requests from every worker at once instead of a few from each. serve answers payloads[i] with http.reply(i, ...); one it leaves unanswered gets 500. A lane is its own process: it opens what it needs, such as its database connection, itself, and the batch it is serving waits on nothing else. While a lane is busy, the next batch gathers; with http.batchWindow set before this call, a batch also stays open until its first request has waited that long. Call before http.fork and listen, on Linux; elsewhere it does nothing and http.relay returns false.

http.relay(lane: int, payload: string) -> bool

Pass the request this handler is serving to lane, one of the lanes http.lanes started, with payload as what that lane's serve is handed. The response the lane replies with is sent to the client, and the worker serves other connections meanwhile. Returns true when the request was passed on, in which case whatever the handler returns is discarded; false under a backend other than http.uring(), outside a handler, for a lane that does not exist or has stopped, so the handler answers itself. If a lane stops while requests wait on it, each is answered 503.

Performance checklist

Measure before tuning, and change one thing at a time. In rough order of how much each step usually buys:

  1. Start with the defaults. The thread pool is the safe choice while handlers might block, and it is fast enough for most services.
  2. Make handlers short. Prepare statements once at startup with db.prepare, not per request. Build fixed SQL once (the dexqu param() templates bind in about a tenth of a microsecond).
  3. On one core with local data, go inline. http.inline() removes the thread handoff, lock and wakeup from every request.
  4. On Linux, go io_uring. http.uring() makes a pass of the loop one system call. Add http.gather once the server is busy.
  5. Group your writes. http.afterBatch turns a flush per request into a flush per batch. http.batchWindow buys bigger batches with a little latency.
  6. Use the other cores. http.listen(port, workers) or http.fork, opening connections after the fork. Use lanes when the workers would fight over one database.
  7. Send less. http.gzip for large JSON bodies, if libdeflate is installed at build time.
  8. Raise the limits for load tests. http.limits sets the connection cap. A single load generator can open only about 64,000 connections to one port, so http.extraPort adds ports to spread them.

For memory, dex profile server.dx reports which lines allocate and hold memory. For SQLite, DEX_SQLITE compiles a pinned amalgamation into the binary instead of linking the system's (see db).

bcryptVerify for each passwords[i] against stored[i], computed side by side: four passwords take about 1.5 times as long as one, so a batch of logins costs well under half the CPU per password. The same answers as bcryptVerify, which handles any pair this cannot (passwords with bytes over 127 among them). One bool per password; false where stored has no entry.

Encryption

crypto.encrypt(keyHex: string, plaintext: string) -> string

Encrypt a secret for storing: AES-256-GCM with a fresh nonce, as base64. The key is 32 bytes as 64 hex digits, from randomHex(32). Returns "" for a bad key. Needs OpenSSL.

crypto.decrypt(keyHex: string, sealed: string) -> string

Decrypt what encrypt produced. Returns "" for a wrong key or input that was altered or cut short. Binary-safe. Needs OpenSSL.

Hashes and MACs

Compare a signature or token with secureEquals, never ==: == stops at the first differing byte, which leaks how much of a guess was right.

SHA-256 of a string, as lowercase hex. Needs OpenSSL.

HMAC-SHA-256, as lowercase hex. Needs OpenSSL.

crypto.hmacSha512Hex(key: string, message: string) -> string

HMAC-SHA512 of a message under a key, as lowercase hex. What Paystack signs webhooks with.

HMAC-SHA-1, as lowercase hex. Only for protocols that require it, such as TOTP; prefer hmacSha256Hex otherwise. Needs OpenSSL.

Compares two strings in time that does not depend on how much of a prefix matched. For signatures and tokens, where == leaks a prefix an attacker can walk.

RS256 signatures

Verify an RS256 signature — RSASSA-PKCS1-v1_5 over SHA-256 — against an RSA public key given as its raw modulus and exponent, which is what a JWK's 'n' and 'e' are once base64UrlDecode has run over them. What checking a Google or Apple ID token needs. False on any failure, including a build without OpenSSL. Needs OpenSSL.

Sign a message with RS256 — RSASSA-PKCS1-v1_5 over SHA-256 — using an RSA private key in PEM form, returning unpadded base64url: a JWS signature as written, so the result is a token's third segment. The private half of verifyRs256, and what minting a Google service-account assertion needs, which is the only way to reach Firebase Cloud Messaging v1. The PEM must have real newlines, not the \n escapes a JSON key file writes. Empty on any failure, including a build without OpenSSL. Needs OpenSSL.

reflectmodule

The reflect module reads a struct's fields by position, so a function can walk a value whose shape it does not have written down — a row mapper, a validator, an audit diff, a debug dump.

import "reflect"

Walking a struct

import "fmt"
import "reflect"

struct User {
    id: long
    email: string
    score: double
    active: bool
}

fn main(): void {
    let unit: User = User { id: 42, email: "ada@example.com", score: 150.0, active: true }

    let i: int = 0
    while (i < reflect.fieldCount(unit)) {
        let name: string = reflect.fieldName(unit, i)
        let kind: string = reflect.fieldKind(unit, i)
        fmt.println("${name} (${kind}) = ${reflect.toString(unit, i)}")
        i = i + 1
    }
}

By reference, and on nested values

The subject may be a struct value or a &T, so a generic helper reads the same either way. A nested struct field and an array element are each subjects in their own right.

fn describe(c: &User): string {
    let sb = StringBuilder()
    let i: int = 0
    while (i < reflect.fieldCount(c)) {
        sb.append(reflect.fieldName(c, i))
        sb.append("=")
        sb.append(reflect.toString(c, i))
        sb.append(";")
        i = i + 1
    }

    return sb.toString()
}

reflect.asString(people[0], 1)    // an array element

What it costs

Reflection here is not the usual trade of speed for flexibility, because the metadata is generated rather than discovered.

Nothing is emitted unless it is used. The compiler records which structs a reflect call names and emits a name table, a kind table and typed accessors for exactly those. A program that does not import reflect is byte-for-byte what it was without the module.

A known field costs what a field access costs. fieldCount and typeName become literals, fieldType reads a table of them, and indexOf with a literal name resolves at compile time — so reflect.asString(unit, reflect.indexOf(unit, "email")) compiles to a constant index into a switch, the same load as unit.email. Only a name computed at runtime searches the name table.

A mismatched read cannot misread memory. Each accessor is generated with a case for the fields of its own type only, so asLong on a string field returns 0 rather than reinterpreting a pointer as an integer. There is no offset arithmetic in the generated code.

Limits

Reflection is read-only: there are no setters, so a struct cannot yet be filled in field by field. Writing would have to release the old value and retain the new one through a generated setter, and that is left for a later version rather than bolted on.

The subject must be a variable, field, or element — not a temporary. A temporary owns its heap fields, and reflecting one would leave nobody to release them, so bind it to a variable first.

dexqulibrary

A SQL query builder. It produces SQL text and the values for its placeholders, for PostgreSQL, MySQL or SQLite. Written in pure Dex, with no C library.

dex get github.com/ensamuel7/dex-modules/dexqu

Needs dex 0.9.16 or later. Source and full README.

import "github.com/ensamuel7/dex-modules/dexqu" as "q"

let active: q.Select = q.from("users u")
    .columns(["u.id", "u.email"])
    .join("orgs o", q.col("o.id").eq(q.col("u.org_id")))
    .where(q.col("u.active").eq(q.boolean(true)))
    .where(q.col("o.plan").in([q.text("pro"), q.text("team")]))
    .orderBy("u.created_at DESC")
    .limit(20)

let built: q.Query = active.build(q.Dialect.Postgres)

built.sql is then:

SELECT "u"."id", "u"."email" FROM "users" AS "u"
JOIN "orgs" AS "o" ON "o"."id" = "u"."org_id"
WHERE "u"."active" = TRUE AND "o"."plan" IN ($1, $2)
ORDER BY "u"."created_at" DESC LIMIT $3

and built.args is [Text(pro), Text(team), Int(20)]. build throws q.QueryError for a query that cannot be written: a feature the dialect lacks, an UPDATE with no condition, or a malformed name.

Three rules

Builders are values. Every method returns a new builder and leaves its receiver alone, so a base query can be shared and branched. A call whose result is dropped does nothing: write s = s.where(...), not s.where(...). A base built at startup can be branched from any number of threads at once.

let base: q.Select = q.from("orders").where(q.col("tenant_id").eq(q.param("tenant")))
let open: q.Select = base.where(q.col("state").eq(q.text("open")))
let recent: q.Select = base.orderBy("created_at DESC").limit(50)

Values are never SQL. q.text, q.integer, q.bigint and q.real become placeholders, with their values in Query.args. There is no interpolated mode. eq(q.sqlNull()) becomes IS NULL.

Names are always quoted. "u.name" becomes "u"."name", so a reserved word works as a column and a name taken from a request cannot become SQL. orderBy accepts only a name and an optional ASC or DESC, so a sort key from a query string is safe to pass straight in.

Build once, run many

q.param(name) is a placeholder whose value comes later. Build the query once at startup and bind it per request: binding costs about a tenth of a microsecond, building about two.

let byEmail: q.Query = q.from("users")
    .where(q.col("email").eq(q.param("email")))
    .where(q.col("deleted_at").isNull())
    .build(q.Dialect.Postgres)

let args: q.Value[] = byEmail.bind().setText("email", email).args()

A Redis client over the hiredis C library.

dex get github.com/ensamuel7/dex-modules/redis

Needs hiredis and pkg-config: brew install hiredis or apt install libhiredis-dev. Source.

import "github.com/ensamuel7/dex-modules/redis"

A Reply has a kind (Text, Number, List, Nil, Status) and the matching text, number or items.

Threads

A Client can be shared by any number of threads. Each command takes a connection from the pool for the length of the command, waiting if all are in use, so two threads never read each other's replies. A connection that drops is redialled the next time it is taken.

Pub/sub

Subscribing takes a connection out of request/reply for good, so r.subscribe opens one of its own rather than taking one from the pool. Messages are pulled, usually from a thread that does nothing else:

let sub: redis.Subscriber = r.subscribe("jobs:node-a")
spawn {
    while (true) {
        let m: redis.Message? = sub.next()
        if (m == null) {
            break
        }

        handle(m.channel, m.payload)
    }
}

A Message has the channel it arrived on, the pattern that matched it ("" for a plain subscription) and the payload.

Lifetime

Database and Statement hold C handles, closed when the last reference to them goes. A statement keeps a reference to its connection, so the connection stays open until its last statement is finalized, whichever order they are released in.

dexdnslibrary

A domain's DNS records at Cloudflare, Hetzner (Cloud API) or a PowerDNS Authoritative server, behind one interface. Pure Dex, using only http and json.

ProviderConstructor
Cloudflarecloudflare(api, token); set comment to tag the records it makes
Hetznerhetzner(api, token); comment likewise
PowerDNSpowerdns(api, key, nameservers, label); label names it in error messages

Each implements the Provider interface: kind, zone (found, or created), list, replace, update and forget. Writes return "" when done, or the provider's reason.

Records are provider-neutral

Names are full, lowercase and without the trailing dot. TXT content is the whole unquoted text, split into 255-byte strings on the wire where a provider needs it and joined back on reading. MX and SRV keep their priority in priority, and SRV content is weight port target. sameValue compares two records the way a provider would.

update touches only what it is given

update drops the drop values, adds the add values, and leaves every other value at that name and type alone, so two programs can share a zone as long as each edits only the records it made. Neither replace nor update compares TTL or proxying: an existing record with the same value is kept.
